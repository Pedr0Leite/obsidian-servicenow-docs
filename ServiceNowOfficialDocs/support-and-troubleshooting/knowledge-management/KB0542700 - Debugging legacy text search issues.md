## Issue

Key tables  

* * *

**ts\_document** _\-_ all searchable records on the instance.  
**ts\_c\_X\_mm** - **_X_** is the number for the table of the respective record (can be identified from the _ts\_index\_name_ table) - **_mm_** is the shard (can be identified from the last digit of the document number).  
**ts\_word** _\-_ all the indexed words.  
**ts\_word\_roots** _\-_ root word. Relationship between word and the stem.  
**ts\_c\_attachment** - table to index attachments  
**text\_search** _\-_ recording searches performed by a user.  
**ts\_search\_stats** _\-_ search suggestions generated from text\_search table by the TS Search Stats job.  
   
   
Order of events when a user does a search (high level view):  

1.  **ts\_query** / **ts\_search\_stats**
2.  **ts\_group** / **ts\_table**
3.  **ts\_stop** / **ts\_index\_stop**
4.  **ts\_word\_roots** / **ts\_word**
5.  **ts\_c\__X_\__mm_**
6.  **ts\_document** (A reference to the record - uses sys\_id of the record.)

   
Order of events when the engine does its indexing (high level view) and the record gets updated/inserted/deleted:  
record gets update/inserted/deleted  
**ts\_document**  
**ts\_word**  
**ts\_stop**  
**ts\_word\_roots**  
**ts\_c\__X_\__mm_**  
**ts\_index** (Represents tables that are indexed. For example, task, cmdb\_ci, etc.)

Cannot find a record

* * *

Q.    Where are they searching?  
               a.    Global (including catalog and kb search, as they are the same), list search.  
Q.     What table is the expected record is in?  
               a.    Can also ask if they are experiencing this for other records on the table.  
Q.     Try to reproduce the issue on the list search ('for text' or 'keywords').  
               a.    Everything else is an addition.  
               b.    Could deduce UI or Text Search issues.  
Q.     If the search results differ between Global and the List search, then there is something different.  
               a.    Check the Text Search Groups and the respective Conditions (this is the case for many of the issues).  
Q.     If the record does match the condition and still cannot be searched, want to check if it is indexed  
               a.     Check in the **ts\_document** table where **_'Document ID' = sys\_id\_of\_the\_target\_record_**  
Q.     If we cannot find a record in the above steps, it could be an indexing issue, so take a note of when the article was last updated.  
Q.     Go to the **sysevent** table and filter on: **_Queue=text\_index_** AND **_Instance=sys\_id\_of\_the\_target\_record_**  
               a.    Should see processed _text\_index_ events for the record (it is indexed and something else is happening).  
               b.    If you see ready events for the record, the record is due for indexing.  
               c.     So check if the indexing has a problem by looking at the count of ready _text\_index_ jobs. Check if the count is increasing.  
               d.    If the state shows **_queued.sys\_id\_of\_index\_job_**, the job is holding the event and will get processed. Should not be an issue.  
8.     Based on 7c we want to check the health of the job:  
               a.    Navigate to **sys\_trigger** table.  
               b.    Look for '**_text index events process_**'.  
               c.     Check which node it is claimed by.   
               d.    If claimed, check the stats/threads of that node to see if it is still running and what it is doing. May be worth tailing the logs for any errors.  
               e.    Can be halted when the reaper is running (pre-Calgary).  
9.     Event job issues:  
               a.    General job health issue. You may find the job is said to be running but not seen on any node.  
               b.    To fix clear the claimed by field and change the state to ready. First take a snapshot of info and document it in the incident.  
10.   No index event:  
               a.    If we do not find the record in ts\_document and there are no text\_index events for that record, we may have an incomplete on that table.  
               b.    Check if there are more records on the table that cannot be searched (need the customer to tell us) Most likely will need to reindex the table (not full) to maintain integrity.  
               c.     If it is just a very few records then do a trivial update (for example, spacer, dot, etc). This will create a new text\_index event for that record.  
               d.    Debug the **sysevent** to check that the index is being created and processed for that record.  
               e.    For the increasing number of index events in **sysevent**, there is a possibility that some would have ended up in previous shards.  
                                           i.    Aspen only indexes the current.  
                                          ii.     Berlin only indexes current and one previous.

Stemming 

* * *

An example of stemming is "I searched for \_\_\_\_\_ and get \_\_\_\_\_ what's up?"

**Session Debug** would be used in this case. 

1.  **Text Search** to understand stemming.
2.  **SQL** to see the involvement of tables to find the words.
3.  Try to reproduce in the table search. This way you get a more refined debug.

Document scoring

* * *

**Detailed in the product documentation: [Zing computes document scores using three components](https://www.servicenow.com/docs/csh?topicname=c_DocumentScoring.html&version=latest "Zing computes document scores using three components")**  
**Scoring:** The higher the number, the higher the record will appear in the search results list.  
**Aspects of scoring:**  

1.  ts\_weight attribute on the field.
2.  Frequency points - the sum of how many times that terms occurs in the record (see the product documentation article above).
3.  Sequence points - the number of words matched in sequence (see the product documentation article above).

**Scoring tools:** It is good SQL practice to check the score per word for one record. The **where** clause is the document number of the record in ts\_document (flags is the weighting score - need to test):

Interpreting the **flags** field:  
The "flags" field is used to encode both weight and attachment number. If the flag value exceeds 255, it is also encoding an attachment number. Index terms in attachments always have the weight of 1, so you can shortcut the weight calculation by simply counting the number of values larger the 255 and adding this to the sum of values less then 255. Or tweek the SQL query to extract the low order byte.

Items to watch for

* * *

1.  **The attachment\_index=true attribute is not cascaded down to child tables. You will need to add this attribute if you want attachments on a child table to be indexed.**
2.  **When changing this for any field, you will need to re-index the table to apply the weights.**
3.  **Contrary to popular belief, the "\*" in a text search is not the same as that on a filter. For a text search, this is a wildcard character, so "\*est" will represent strings ending with "est" (LIKE "%est"). In a list filter this is used for a _contains_ search (LIKE "%est%").**

## Resolution

Performing a full re-index

* * *

**The only recommended way to trigger a re-index of a table in the platform is to use the text\_index events. This is by using the **Regenerate Text Index** UI Action on a Text Indexes \[ts\_index\_name record\]:**

-   Navigate to System Definition → Text Indexes
-   Select the affected table from the list
-   Under the Related Links heading click on Regenerate Text Index
